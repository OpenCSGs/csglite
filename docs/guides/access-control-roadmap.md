# CSGLite Access Control Roadmap

CSGLite 已有本地 API Key、调用用量统计和 Provider Pool 限流。下一步应补齐用户身份、团队归属、资源授权和调用额度，使一台 Lite 或一个 Lite 集群可以供多个团队共享，并能回答“谁可以调用什么、可以用多少、谁修改了权限”。

建议按 **统一鉴权 → OIDC 登录与用户团队 → 模型授权 → 配额与预算 → 企业组织治理** 推进。首个可试用版本交付前三项；团队用量治理版本再加入配额与预算。个人桌面使用继续保持轻量。

状态：规划草案，尚未实现。对比日期：2026-11-15；CSGLite 基线为 `a021eaa` 及当前工作区。参考实例为 [本地 LiteLLM Access Control](http://localhost:4000/ui/teams/)，页面显示版本 v1.104.0，Docker 镜像标签为 v1.104.0-dev.2。

| Internal Users | 用户邀请、批量邀请、全局角色、团队/组织归属、状态、SSO ID、用户 Key 及支出/预算；邀请邮件依赖邮件服务 | 有本机云账号登录和桌面会话，缺少 Lite 自身的多用户身份及角色体系 | M1 含基础 OIDC；组织级身份治理放 M4 |

### 第三方登录与人员管理

LiteLLM 支持 Google、Microsoft Entra ID、Okta 和 Generic OIDC 登录；首次 SSO 登录可创建用户并应用默认设置，角色及团队可按身份源字段映射，无需逐个人手动建账号。参考[官方 OIDC 文档](https://docs.litellm.ai/docs/proxy/admin_ui_sso)、[用户自助管理](https://docs.litellm.ai/docs/proxy/self_serve)及[SSO 权限映射](https://docs.litellm.ai/docs/proxy/access_management/sso_permissions)。当前权限文档要求通用 OIDC 的团队 claim 匹配已存在的 LiteLLM 团队；自动创建团队的行为需按具体版本和身份源验证。

CSGLite 将基础 OIDC 纳入 M1：管理员配置身份源及“身份源组 → 本地团队/角色”规则，用户首次登录自动建档，随后在团队权限内自助管理 Key。本地管理员账号保留为初始化与恢复入口；多组织身份治理、SCIM 同步和 SAML 放在 M4。

### 必须先补齐的权限边界

当前 `requiresRemoteAPIAuth` 按路径枚举，包含 chat、responses、部分模型操作及集群管理，但没有统一覆盖所有管理和推理路由。例如 `/api/api-keys`、`/api/settings`、`/v1/embeddings`、图像与音频部分入口不在此枚举内；具体风险还取决于运行模式、监听地址和 handler 自身约束。现有桌面会话、跨域保护和集群 mTLS 各有用途，不能替代多用户授权。

因此 M0 必须建立完整路由权限清单，并用测试确认执行效果。只增加 Teams 页面无法形成可安全使用的团队产品。

## 分阶段交付

以下为排期估算，假设 1 名后端、1 名前端持续投入，并有测试支持；每阶段含集成验收。M0–M2 累计约 6–8 周，M0–M3 约 9–12 周，M4 另需约 3–5 周。人力、身份源对接和多入口集群范围变化后应重新估算，不绑定发布版本或承诺日期。

| 阶段 | 优先级与工期 | 用户可获得的结果 | 依赖与完成标准 |
| --- | --- | --- | --- |
| M0 统一鉴权基础 | P0，1–2 周 | 可明确选择个人模式或团队托管模式；托管入口区分管理身份与推理 Key | 全路由分类、管理员引导、可信代理边界、拒绝策略、基础审计；鉴权覆盖测试通过后进入共享试用 |
| M1 OIDC 登录与用户团队 | P0，3–4 周 | 企业账号登录、首次登录自动建用户、组到团队及角色映射；用户自助管理 Key，支持过期、暂停及轮换 | 依赖 M0；OIDC 登录与撤权验收通过，本地恢复可用，无跨团队读写 |
| M2 模型与资源授权 | P0，约 2 周 | 用 Access Groups 批量授予模型或 Pool 的调用权限；不同团队只看到并调用获准资源 | 依赖 M1；所有协议、模型别名、Provider 直连及 Pool fallback 无越权旁路；完成团队访问控制 MVP |
| M3 配额与预算 | P1，3–4 周 | 按团队、用户、Key 配置 RPM/TPM/并发、周期 Token 额度及金额预算，查看用量与超额原因 | 依赖 M1–M2 的归属和授权；并发预占、流式结算、重启恢复、周期重置通过验证；完成团队用量治理版 |
| M4 企业组织治理 | P2，3–5 周 | 多组织、组织级身份治理、SCIM/SAML 扩展、审计导出和组织报表 | 依赖 M1–M3；组织数据隔离、身份解绑、停用回收及 License 生命周期通过验证 |

### M0 统一鉴权基础

- 为路由登记公开、推理、管理、内部节点四类用途；未知路由在托管模式默认拒绝。模型发现、文件下载、异步任务及 WebSocket 同样纳入清单。
- 建立统一调用身份，至少区分本机管理员、用户会话、推理 Key、内部节点。推理 Key 不获得修改设置、签发 Key、安装应用或读取其他用户日志的权限。
- 托管模式显式开启，初始化首位管理员并提供本机恢复流程；登录采用可失效的会话。对管理写操作校验来源并防止跨站请求，登录入口限制尝试频率。
- 托管入口即使经本机反向代理转发，也不能因 TCP 来源是 loopback 而绕过身份校验。转发头只信任明确配置的代理。
- 首次加入可追责的管理事件：登录、Key 签发/吊销、鉴权模式变更。审计事件记录操作者、动作、对象、结果和关联请求 ID，不记录凭据明文。

**验收：** 覆盖远程/本机、托管/个人、有效/无效/无 Key、浏览器/非浏览器、代理转发等组合。托管模式未认证请求不能操作管理 API；推理凭据不能升级为管理员。个人模式及桌面 sidecar、CLI 和现有客户端回归通过。

### M1 OIDC 登录与用户团队

- 增加用户、团队、成员关系，支持创建、邀请、移除和停用；用户可加入多个团队，每个 Key 明确绑定一个调用团队。
- 第一版使用内置角色：实例管理员、团队管理员、成员、只读审计员。团队管理员只在本团队授予已有权限，不能提升为实例管理员；保护最后一位实例管理员。
- 首版接入一个可配置的通用 OIDC 身份源，采用 Authorization Code + PKCE；配置 issuer/discovery、client ID、受保护的 client secret、回调地址和 scopes。校验签名、issuer、audience、有效期、state 和 nonce；以 `(issuer, sub)` 关联本地用户，不按可变邮箱自动合并账号。
- 首次登录自动创建本地用户并应用最小权限默认值。管理员配置允许登录的身份源组、角色字段和组到团队的显式映射；首版只加入预先建立并授权的团队，未知组不自动建团队或获得权限，管理员角色必须显式授权映射。
- 登录时同步身份源管理的角色及成员关系，移除已撤销的授权；区分人工分配和身份源分配的成员关系。设置会话及身份授权有效期，过期后重新验证；个人 Key 同样受主体有效状态约束。M1 不承诺身份源停用的即时推送，SCIM/事件同步在 M4 补齐。
- 提供 OIDC 登录入口和连接测试、字段映射、登录限制配置；实例管理员可查看映射结果和失败原因。OIDC 用于控制台登录，推理调用继续使用受团队授权约束的 API Key，不默认接受任意身份源 access token。
- 保留本地用户登录、一次性限时邀请链接及账号恢复，支持没有身份源的离线部署；启用 OIDC 后仍保留受控的本地管理员恢复入口。SMTP 与批量邀请可后置。现有 CSGHub 云账号登录继续负责上游凭据，不自动授予本地管理员权限。
- 扩展现有 Key：所有者、团队、状态、过期时间、用途说明；支持轮换及有界宽限期。删除或吊销后保留稳定 Key ID 与历史用量关联。
- 用户停用时撤销其会话和个人 Key；成员移出团队时撤销其在该团队的授权。服务账号作为独立主体后续扩展，避免长期任务依附离职员工。
- 提供用户、团队、成员及团队 Key 页面；团队默认设置只影响新对象，修改存量对象需要明确展示影响范围。

**验收：** 团队 A 无法查询或修改团队 B 的成员、Key、用量、日志和任务；直接使用对象 ID 访问也被拒绝。过期/暂停 Key 被拒绝，轮换后旧 Key 按期限失效，历史统计不丢失。

**OIDC 验收：** 至少使用一个标准身份源完成端到端验证：首次登录建档、再次登录复用身份、组/角色映射、未授权用户拒绝、撤组后权限收回。邮箱变化不产生新账号，同名邮箱不能接管已有账号；无效 token、回调重放和错误 state 被拒绝。身份源不可用时不绕过登录限制，本地恢复仍可用；明确并验证会话及个人 Key 的最大撤权延迟。

### M2 模型与资源授权

- 增加 Access Group：首版资源为本地模型、云模型、第三方 Provider 模型及公开 Pool；复用现有资源 ID，不再维护第二份可编辑模型目录。
- 团队获得资源组授权，用户/Key 可进一步收窄。组内资源取并集，最终调用范围受所属团队、主体和 Key 的显式限制共同约束，禁止 Key 自行扩大团队权限。
- 明确区分“不额外限制”和“无权限”；空授权默认无权限，全模型授权必须显式选择，不能用空数组隐含放行。
- 列表与实际调用共用同一策略；服务端负责执行，UI 显示用户可理解的拒绝原因。Key 创建页只允许选择签发者有权授予的资源。
- 将模型别名解析到稳定资源身份。授权调用 Pool 表示允许执行该 Pool 配置的成员，但不自动授予直接调用成员的权限；修改成员集合属于授权影响变更，必须校验管理员权限并审计。
- 观测数据、会话、图像任务、结果下载和导出按所有者/团队过滤。对全局管理资源采取管理员专用策略，避免依靠前端隐藏入口实现隔离。

**验收：** 同一未授权模型通过 OpenAI、Anthropic、原生 API、Provider 路径、别名均不可调用；已授权 Pool 的正常 fallback 可用，但不能借此直连未授权成员。调整组权限对新请求立即生效，并为已建立流式/实时会话定义撤权处理。

### M3 配额与预算

- 建立可复用额度策略，绑定团队、用户或 Key；各层限制共同生效。Provider Pool 成员限流继续独立保护上游，页面明确展示当前触发的是哪一层限制。
- 先落地 RPM、TPM、最大并发和周期 Token 硬额度，再加入金额预算。Lite 尚无本计划覆盖的 batch 工作流，不直接移植参考实例的 batch TPD；日 Token 配额按同步/流式调用另行定义。
- 金额预算明确币种、周期、软阈值、硬上限和重置时区；未知价格不当作零成本。未定价本地模型默认按 Token/请求额度治理；金额硬预算需完整定价，或显式拒绝无法计价的调用。
- 推理前原子预占，完成后按实际 usage 核销并释放余额；流式请求按最大输出范围预留，明确中断、失败、取消和未知 usage 的计费规则。每个请求的结算应幂等。
- 持久化余额和预占记录，处理崩溃恢复、并发超额、跨周期在途请求及重复回调。重试/多次上游尝试分别记实际成本，调用者请求数按统一规则统计。
- 在现有用量页增加团队/用户/Key 过滤、额度剩余、重置时间和 CSV 导出；加入阈值告警与超额拒绝事件。首版站内提示，外部通知渠道可后续接入。

**验收：** 并发压测不能通过竞态绕过硬限额；未知 usage 有保守处理并可核对；服务重启不重置预算；流式断开不泄漏并发槽位；多币种不能直接相加；报表与额度账本可按请求关联核对。

### M4 企业组织治理

- 在实例内增加 Organization → Team 层级，提供组织管理员和组织范围报表；组织归属进入授权上下文，组织切换不沿用其他组织权限。
- 在 M1 通用 OIDC 基础上扩展组织级身份源配置、组到组织的映射及跨组织账号关联规则；私有化 CSGHub 身份对接按其协议适配。
- 支持服务账号、成员批量导入和停用回收；通过 SCIM 或身份事件同步用户及组变化，缩短离职撤权延迟。SAML 及更细自定义角色按实际客户需求分别排期，不作为第一版团队能力前置条件。
- 扩展审计查询、保留周期、导出和外部归档，记录授权策略、团队角色和预算变更；本地普通日志不宣称具备不可篡改保证。
- 评估 MCP、Agent、AI Apps、数据集及集群资源授权。只有资源稳定标识、服务端执行入口及所有权模型具备后，才加入 Access Groups。

**验收：** 跨组织读取、直接 ID 访问和导出均受隔离；身份源停用后按约定时限回收会话及 Key；组织迁移不改写历史账单归属；License 失效不导致已有权限限制被静默放开。

## 实现约束

### 数据与迁移

`config.json` 只放必要的实例级设置，复用或扩展已存在的同域结构。用户、成员、授权、Key 和预算是业务状态，不能散落为多个重叠顶层配置项。

建议在存储根下建立独立访问控制 SQLite 库，沿用仓库已使用的 SQLite 技术栈；与可清理的观测数据库分开，避免清理请求日志时删除权限或预算账本。M0 评审时确定最终路径和 schema，所有运行文件、迁移备份和临时输出均在配置的 storage root 下。

迁移 `api_keys.json` 时保留 ID、哈希、名称、创建时间及最近使用时间，历史 Key 归入显式标记的 legacy 主体；托管启用时由管理员确认授权范围。迁移完成后停止旧文件写入，兼容旧 API 的读写通过新存储完成，不维持两份可写 Key 真相。`api_usage.json` 的既有数据保留为历史统计，不将其聚合记录直接当作可事务扣减的预算账本。

迁移需覆盖重复执行、失败恢复、备份与旧版本回退流程；新增字段必须有 round-trip 及旧配置兼容测试。历史请求保存发生时的团队/组织归属，不因后来成员移动而改变历史报表。

### 单机与集群

首版以**单个受控入口**为权限及预算执行点；节点 mTLS 身份继续用于计算节点互信，用户 Key 不转发到执行节点。传递受信任且最小化的内部关联信息，客户端不能伪造团队身份；涉及 CSGHub Edge 的请求继续遵守已有调用者隐私约定。

多入口分别维护本地计数不能保证全局预算。若后续开放多个入口同时服务同一团队，必须先选择单一额度权威或一致的共享账本，并明确网络分区时的拒绝策略；在此之前仅承诺单入口配额准确性。与[公网集群方案](public-cluster-requirements.md)共同评审，不能以节点数 License 配额代替调用方用量配额。

### 兼容性与版本边界

- 保留已发布的个人/桌面模式和推理入口使用约定；团队托管能力采用显式启用及迁移，不静默改变桌面固定推理监听器。桌面协议变动需联测 `csglite-client`。
- 复用 `/api/api-keys` 与 `/api/api-usage`，新增字段和筛选参数优先采用兼容扩展；托管模式下按身份限定返回范围。未来新增 users、teams、access-groups、budgets 管理 API 时再同步 OpenAPI，本规划不提前发布不存在的接口。
- API 实现与 `openapi/local-api.json` 同步，运行 `go test ./internal/server`；前端新增文案同时提供中英文。前端变更按仓库规则构建、同步静态文件并仅在 `localhost:11435` 验证。
- macOS、Linux、Windows 均需验证存储、迁移、权限和登录流程。SQLite 及会话实现不得引入平台专属依赖。
- M0 的基础权限修复及既有 CE Key/用量能力保留 CE。新团队功能建议使用统一实现，以用户/团队数量区分规模；基础 OIDC 随 M1 交付，商业门控单独评审；组织级身份治理、SCIM/SAML 与多组织能力可作为新增 EE 能力。具体门控键和额度须经产品评审，统一登记 `internal/license/features.go`，遵守[EE 规则](../agent-guidelines/ee-features.md)。

## 第一批开发任务

| 顺序 | 可独立评审的交付物 | 完成条件 |
| --- | --- | --- |
| 1 | 路由权限矩阵与运行模式设计 | 列出全部现有入口、调用身份、动作、资源及个人/托管行为；确认代理与桌面边界 |
| 2 | 身份上下文和统一鉴权 | 接入现有 Key 与桌面会话；管理/推理权限分离，建立路由覆盖与越权测试 |
| 3 | 存储 schema 与迁移 | 用户、外部身份绑定、团队、成员来源、Key、会话及审计表；旧 Key 无损迁移，单一写入来源 |
| 4 | 管理员引导与成员流程 | 管理员初始化、登录、一次性邀请、退出、停用及恢复可在离线内网完成 |
| 5 | OIDC 登录与身份映射 | 标准身份源联调、首次登录建档、稳定身份绑定、组/角色同步及撤权时限验收通过 |
| 6 | Teams 与 Internal Users 页面 | 身份源配置与映射、团队/成员增删、内置角色、Key 归属、过期、暂停及轮换前后端贯通 |
| 7 | Access Groups 与授权执行 | 模型/Pool 授权、列表过滤、各协议和异步对象隔离通过验收，发布 MVP |

开始编码前需在 M0 设计评审中确定：托管模式启用与回退方式、首版角色矩阵、Key 迁移默认授权、OIDC 联调身份源、组/角色映射规则及会话与 Key 的最大撤权延迟。M3 再确定金额定价来源和周期语义；M4 再确定组织级身份治理、SCIM/SAML 对接范围和商业额度，避免将后续决策阻塞在第一版团队交付之前。
